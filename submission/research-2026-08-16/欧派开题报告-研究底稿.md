# 欧派命题开题报告：研究与方案底稿

> 用途：这是报名阶段的“思考底稿”，不是最终提交文案。它把外部证据、你的核心判断、可落地边界和待决定问题放在一起，方便你逐段确认“这是不是我真正想说的”。
>
> 当前方向暂称：**AI 家装共识层**。名称可以最后再定。

## 0. 先把命题说清楚

欧派不缺设计、报价、生产和安装等下游能力；它真正值得补的一层，是把客户模糊且会变化的偏好，变成一份：

1. 客户看得懂、愿意确认的视觉化方案；
2. 设计师可继续修改的结构化设计意图；
3. 报价、生产、交付可以直接接续的“确认版本”。

因此，本方案**不是再造一个 AI 生图工具或 3D 家装软件**，而是连接“客户表达”和“既有设计、报价、交付系统”的低成本共识层。

一句话版本：

> 用可视化对话、点选修改、版本确认与变更影响说明，把“我大概想要这样”转化为可执行、可追溯的定制家装共识。

## 1. 你已经提出、应保留的核心判断

| 你的判断 | 在方案中的位置 |
| --- | --- |
| 客户一开始往往说不清自己想要什么；纯问卷或“您好，请描述需求”会降低体验。 | 第一轮交互要从“被理解的视觉选择”开始，而不是泛泛提问。 |
| 客户是靠看见、比较、点选和修改，逐渐发现自己真正喜欢什么。 | 用现有 3D 设计或渲染能力生成候选空间，并允许点击墙面、柜体、布局等对象提出局部变化。 |
| 用户不愿打很多字。 | 文字、语音、标签、图片参考和对象点选应同时存在；点选是降低表达成本的入口。 |
| 生图不是最终交付物；结构化 JSON 才能支持真正定制、报价和下游执行。 | 每轮对话与点选都沉淀为“设计意图 JSON 加版本记录”，而不是只保存一张效果图。 |
| 客户必须确认一个最终满意版本，否则不断改动会传递为返工、加价和不信任。 | 设计、报价、交付之间建立“确认版本”和变更影响说明。 |
| 公司会更喜欢低投入、高效率的方案。 | 不新建渲染、报价、生产系统；飞书负责共识协作层，通过 API 对接既有工具。 |

## 2. 外部事实与可得洞察

### 2.1 欧派已有的能力，决定我们不该重复造什么

- 欧派 2024 年报写明，其业务覆盖个性化设计、研发制造、销售、安装等一体化服务；门店侧可根据户型、偏好、功能和选材生成 3D 可视化方案。客户确认后，订单可进入数字化平台生成 BOM、排产和加工信息。[1]
- 欧派官网目前展示的消费流程包含预约量尺、设计师沟通需求、约 3 个工作日出图、门店看效果并满意后签约、配送安装。[2]
- 欧派的 AI 宣传材料已展示“根据户型、习惯、图纸生成方案”、3D 呈现和供应链数据联动等方向。[3]

**由此得到的方案边界：**不把“AI 生成效果图”当作创新终点，而把重点放在“客户为什么认同、改动后影响什么、哪一版能进入下游”。

### 2.2 痛点并不只在设计速度，而在确认与变更

- 上海市消保委公开提示，在 280 余件家装投诉中，超过一半与合同增项有关；量房不清、合同与实际偏差、材料数量或翻新需求改变都可能带来额外费用。[4]
- 库润数据《2024 年中国家装消费调研报告》显示，消费者普遍会比较多家服务商；材料质量、费用透明合理、设计效果及还原度、施工工艺都是高频决策因素。[5]

**可写进洞察的结论：**客户不是只要一张“好看的图”。他还需要相信：这张图真能落地，改了以后我会知道代价，最终签下来的就是我看到并理解的那一版。

### 2.3 竞品已经做到什么，不能把它当作本方案的独特性

- 酷家乐已公开“AI 意向方案”“局部位置替换”“实时渲染”“3D 深化”等能力；其文档也明确指出，输入不准确会把返工推到后续环节。[6]
- 尚品宅配的公开案例已展示：从需求分析、空间拆解、单空间智能设计到方案包装，并连接报价和生产的流程。[7]

**竞争空白：**“点击局部修改”本身不是新意；更有价值的差异是把每次改动识别为偏好、约束或已确认决策，并把影响解释和版本确认做成标准流程。

### 2.4 用户反馈可如何使用

公开投诉可作为**单个情境证据**，不能当作统计结论。例如，有消费者投诉全屋定制电视墙实际尺寸、样式与设计图差异明显。[8]

报告中应避免写“用户普遍都认为……”，更稳妥的写法是：

> 公开投诉中已出现“设计图与实景不一致”的典型情境；结合家装投诉中合同增项占比较高的监管提示，可推断设计确认与变更记录需要前置、标准化。

## 3. 建议的问题重新定义

### 原始命题的表述

流程长、协同碎、导购能力不一、报价易错、方案修改慢、服务过程不透明。

### 我们的切入点

把问题收敛到一个更可做、也更靠近客户决策的节点：

> **在“第一次沟通”到“方案签约”之间，怎样让客户低成本表达偏好、快速看见可信候选方案，并确认一份可下传的设计版本？**

### 为什么从这里切入

1. 前端意图不清，会把返工、报价变动、延期风险一路传到后端；
2. 只优化后台协同，客户仍会觉得“看不懂、改不动、不敢信”；
3. 欧派已有设计、供应链和服务能力，前端共识层更容易以试点方式接入，而不需要重做全链路。

## 4. 方案骨架：AI 家装共识层

### 4.1 一条完整但不过度扩张的链路

视觉化首问 -> 意图澄清 -> 候选空间 -> 点选或对话修改 -> 结构化版本 -> 影响说明 -> 客户确认 -> 既有报价、生产、服务系统

### 4.2 五个核心模块

#### A. 视觉化首问：让客户觉得“它懂我”，而不是让客户填问卷

客户只需给出最低门槛信息，例如“4 个人住、欧式、希望客厅舒服”或上传户型图、参考图。AI 不用官腔追问，而是给出两个有差异的生活方式候选方向和少量高信息量选择。

示意，不是最终话术：

> 我先按“四人长期居住、希望欧式但不压缩公共空间”做了两个方向：
> A 保留更开阔的会客区；B 用更多收纳换取更整齐的视觉。
> 你更介意“客厅不够放松”，还是“东西没有地方收”？

这里的关键不是文案花哨，而是每次问题都能减少一个真实决策的不确定性。

#### B. 可点击的空间表达：少打字，直接改眼前的东西

在已有 3D 空间或方案缩略图上，客户可以：

- 点墙面、柜体、灯光、布局或某个功能区；
- 说“这里想更亮”“这个柜子不要这么高”“我想要更有欧洲老房子的感觉”；
- 从少量推荐中选“保守改、风格改、预算优先改”。

AI 把自然语言和对象点选翻译成结构化变更，而不是只重新生成一张无法追溯的图。

#### C. 设计意图 JSON 与版本库：把“感觉”变成可执行状态

每个方案都有一个机器可读的设计意图对象。示意字段：

    household: 四人居住、经常会客
    hardConstraints: 预算区间待确认、公共区域要开阔
    softPreferences: 欧式、暖光、收纳多
    spaceDecisions: 客厅电视墙、米白石材、已确认
    changeLog: 每次对象变更及影响
    confirmedVersion: v3

字段应区分三类：**硬约束**（不能违背）、**软偏好**（可继续探索）、**已确认决策**（下游默认不再随意改动）。

#### D. 变更影响说明：每次“想改一下”先看代价

当客户修改关键对象时，系统不只显示新图，还显示可理解的影响卡片：

- 预计报价区间变化；
- 对材料、工艺或定制周期的影响；
- 是否影响已确认空间；
- 是否需要设计师复核；
- 当前版本与上一版的可视化差异。

只有客户点击“保留此改动”并完成必要确认，变更才进入下一版本。这样把“反复试试”与“正式确认”分开。

#### E. 确认版本与下游交接：让方案不是停在好看的图上

当核心空间与关键预算、工期边界被确认后，生成一份“客户共识单”：

- 已确认方案缩略图与版本号；
- 关键生活需求与不可妥协项；
- 已确认材料、布局、收纳、预算边界；
- 未决事项和设计师待复核项；
- 每次关键变更及其影响。

此共识单与结构化 JSON 一起交给欧派既有设计、报价、BOM、生产和售后系统。**下游系统仍由欧派现有能力负责，本方案只减少前端失真和无效沟通。**

## 5. 关键状态设计

| 状态 | 含义 | 是否可进入下游 |
| --- | --- | --- |
| exploring | 客户在看候选方向，偏好仍不稳定 | 否 |
| drafting | 已有空间方案，但存在待确认项 | 否 |
| impact_review | 某项修改正在显示报价、工期、施工影响 | 否 |
| customer_confirmed | 客户确认当前版本和关键边界 | 可进入设计师、报价复核 |
| designer_verified | 设计师确认结构化信息可执行 | 可下传既有报价、生产系统 |
| changed_after_confirm | 确认后又发生改动，需要重新显示影响并确认 | 暂停原下游版本 |

这张状态表是方案的业务核心之一：它把“客户满意”和“企业可执行”区分开，再用设计师复核把两者连接起来。

## 6. 飞书 AI 工具在方案中具体做什么

### 6.1 不把飞书说成渲染软件

飞书不承担 3D 建模、图像渲染、报价算法或生产排程。它承担的是**对话、记录、协作、审批、自动提醒与外部系统连接**。

### 6.2 可行的工具分工

| 飞书能力 | 在方案中的任务 | 需要的企业条件 |
| --- | --- | --- |
| Aily 或 AI Agent | 多轮澄清客户表达；按 JSON 输出偏好、约束、待确认项 | 配置企业知识、流程和模型权限 |
| 多维表格 AI 字段 | 从对话和备注提取需求、分类、摘要、置信度 | 建立需求、版本、变更、任务数据表 |
| 多维表格工作流与自动化 | 版本变更后通知设计师；关键确认后创建报价复核任务；记录异常 | 配置状态、责任人和消息通知 |
| 飞书低代码 | 做面向客户或门店的“方案卡片、热点点选、版本对比”界面 | 需要与渲染图或设计系统 API 对接 |
| 连接器或 HTTP API | 将已确认 JSON、版本号、素材链接传入欧派既有设计、报价工具；回传影响结果 | 企业提供受控 API、字段映射和权限 |

### 6.3 最低成本的试点方式

不建议一开始覆盖“整家全链路”。可以先选一个高频、规则更明确的场景做试点，例如一个客餐厅方案或一个定制柜类空间：

1. 客户在飞书低代码页完成首轮表达和点选；
2. Aily 产出需求 JSON 与待确认项；
3. 现有设计工具返回 2 至 3 个候选图或链接；
4. 多维表格保存版本、关键对象改动和确认记录；
5. 工作流把“已确认版本”推给门店设计师复核；
6. 复核通过后再进入既有报价、生产流程。

**注意：**上述 API 对接是试点假设，不应写成已经具备。报名稿应写“可通过企业现有设计、报价接口或文件导入方式接入”。

## 7. 与常规 AI 家装方案的区别

| 常规做法 | 本方案强调什么 |
| --- | --- |
| 让 AI 快速出图 | 让客户看懂并逐步确认“这是不是我的家” |
| 一次生成后反复重做 | 每次改动被记录为结构化变更，并显示影响 |
| 只保存效果图 | 保存偏好、约束、对象决策、版本和确认记录 |
| 设计师后续重新问一遍 | 设计师接收可读、可追溯的客户共识单 |
| 以“更聪明的模型”为卖点 | 以“更低沟通成本、更少返工和更可控确认”为卖点 |

### 7.1 用可计算对比替代“看起来更好”

以公开用户案例中的 3.1m 客厅进深、350mm 满墙柜、1.1m 常态沙发和 1.6m 展开沙发为基础，再用明确标注的模拟墙体参数比较三类方案：

- 满墙柜改为 300mm 浅柜，中央净距只增加 50mm，不能单独解决压迫感；
- 低柜加双侧高柜可将电视墙立面占用代理由 77.1% 降至 45.8%，但客厅本地几何储物容积同时下降约 42.9%；
- 将缺失储物补偿到玄关后，本模型的全屋几何储物容积可恢复至基准附近（+0.4%），但柜体立面工程量代理约增加 2.7%，因此不能同时承诺“更开阔、同等收纳、价格更低”。

这正是“影响卡片”应向客户展示的内容：AI 不替客户隐藏取舍，而是计算空间、收纳和工程量差异，并让客户确认。完整输入、公式、限制与可复算脚本见同目录的 `电视墙方案对比计算.md` 和 `calculations/tv-wall-comparison.mjs`。上述结果是几何推演，不是欧派真实报价或业务效果数据；沟通轮次、返工率等指标仍需企业对照试点验证。

## 8. 报名表两段文字的写作骨架

### Part 1：命题前置分析与洞察（建议 50 至 300 字）

不要先写“AI 很强”。建议按这个顺序压缩：

1. 欧派已有设计、报价、生产一体化基础，但客户从量尺到出图、确认、签约之间仍存在理解和确认断点；
2. 外部证据：家装投诉中合同增项、设计还原与费用透明问题明显；
3. 竞品已能快速出图、局部改图，真正缺口是把模糊偏好转化为客户确认且能下传的版本；
4. 因而提出“AI 家装共识层”。

### Part 2：整体解决方案设计（建议 300 至 600 字）

建议按下面五段写，而不是堆技术名词：

1. **方案概述（约 70 至 100 字）**：一句话讲“视觉化对话、JSON、确认版本、下游交接”。
2. **架构与模块（约 130 至 180 字）**：首问、点选改动、版本库、影响说明、设计师复核、飞书工作流。
3. **创新点（约 70 至 100 字）**：不是生成，而是“意图确认、变更共识、可执行交接”。
4. **价值（约 50 至 80 字）**：缩短确认轮次、减少重复沟通、降低因未确认改动造成的返工、增项争议；量化指标写成试点目标，不虚构已实现数据。
5. **可行性（约 50 至 80 字）**：复用现有 3D、报价、生产系统；飞书承担协作与轻量前台；先从单空间或单品类试点。

## 9. 现在还没有想清楚、但必须在最终稿里做选择的地方

下面不是“缺点”，而是你下一轮思考最值钱的部分：

1. **首问到底长什么样？** 是两张候选方案、生活方式卡片、户型图热点，还是三者组合？第一轮只能选一种主交互，不能写成什么都有。
2. **什么算客户确认？** 是确认设计方向、确认每个关键对象，还是确认预算和工期边界后才算？需要给出最小规则。
3. **变更影响先算什么？** 首版只承诺预算区间、工期、设计复核，不承诺精确报价；精确性边界要写清。
4. **试点品类是什么？** 整家太大。厨房、衣柜、客餐厅或“一个完整空间”需要选一个，才能让方案显得可落地。
5. **谁使用飞书页面？** 客户、导购、设计师各看哪一层？不要让客户直接面对复杂企业表格。
6. **成功怎么衡量？** 建议选择 3 个可验证指标：首次方案确认轮次、设计师重复沟通时长、确认后重大变更率或报价复核耗时。
7. **企业系统怎么接？** 报名阶段可写接口或文件导入的假设；进 40 强后再向企业导师确认真实系统和字段。

## 10. 可选附件的最小构成

报名阶段不需要完整 Demo。可选附件只要做成 4 页左右的 PDF，就能证明你不是空泛想法：

1. 一张“客户从模糊表达走到确认版本”的流程图；
2. 一张客户点击某个对象后的“变更前、变更后、影响卡片”线框图；
3. 一张意图 JSON、版本库和欧派既有系统之间的数据流图；
4. 一张飞书能力映射和试点 KPI 表。

附件结构见同目录的“欧派开题报告-可选附件结构.md”。

## 12. 写作纪律

- 不虚构“AI 让转化率提升 XX%”。所有数字先写为“试点目标”或“拟验证指标”。
- 不写“飞书可以自动生成真实 3D 家装”。渲染和专业设计软件仍由企业现有系统承担。
- 不写“客户不需要设计师”。设计师在可执行性、材料工艺、异常处理和最终复核中仍然关键。
- 不把“酷家乐已有的点击修改”包装成首创；首创点放在确认机制与下游可执行性。
- 最终提交前，把每个外部事实都回到原链接核对一次，避免误读营销材料或旧数据。
