## 会直接影响答辩的三个事实问题

### 固定演示不能证明在线模型理解

当前 `app/src/App.jsx` 的 `runAgentPrompt` 先调用 `findRecordingScenario(input)`。命中时依次等待 3500、4000、4500、5000、3000 毫秒，共 20 秒，再执行本地 `runRecordingScenario`；没有在这条分支调用在线模型。

`app/src/demo/recording-scenarios.js` 为三条精确输入预置命令和回复，并将 trace 来源写为 `demo-script`。因此，不能把固定句的成功率、阶段提示或 20 秒等待解释成模型泛化效果和真实推理耗时。

这些命令仍然通过场景命令入口执行，因此可以作为预设流程演示。它的价值应当由可见变化、规则结果与确认行为来证明。在线能力需要未命中预设的输入及实际 provider trace；还要检查是否走到其他本地路径或异常降级，不能只凭“换一句话”认定在线调用成功。

### 餐桌与人数需要一起核对

原录屏脚本写“保留现有餐桌”，提交正文和当前固定场景代码写“方桌换三座圆桌”。当前代码实际调整尺寸、替换模型路径，并删除一把餐椅；文案还混用“陈家四口”与夫妻加一个孩子的家庭设定。

本稿统一为“三口常住、祖父母偶访”的示例，并暂不承诺圆桌满足来访后的全部用餐需求。三个常住成员再加两位长辈，三张餐椅显然不能单独证明五人共同用餐。必须区分“客厅坐得舒服”和“能同时就餐”，让演示需求、座席能力、画面和旁白一致。

本轮没有为了匹配讲稿修改产品。修改对照也不代替用户对下一开发 Gate 的验收。

### Aily 的历史验证要按记录拆开

`submission/DEPLOYMENT-STATUS.md` 记录的是 2026-08-16 一次真实只读检查，返回 0 个场景命令，并有事件写入回读。它本身不证明 Aily 修改了空间。

项目 README 另有更早的 CLI 真实工具回合记载；不能因此断言 Aily 从未执行过工具，也不能用 CLI 历史成功证明当前网页设计链路。需要让每项成果对应具体日期、入口、版本、动作及结果。

当前 `app/server/consensus-secretary.mjs` 将 Aily 摘要约束为无工具调用，只整理已有事实。设计 Provider 在 `app/server/index.mjs` 按配置选择；配置 DeepSeek 时优先使用相应路径。当前服务实际用了谁，须以该次运行记录为准。

5. 已有证据和待试点测量指标，不混成一张成绩表。
6. 一个真实品类如何进入门店或设计团队试点。
7. 团队、企业协作请求与结尾。
