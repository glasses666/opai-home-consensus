# OPAI 半决赛｜7 分钟核心讲稿

状态：已按 2026-09-09 隔离候选的真实 DeepSeek、Base、Aily 与 RAG 证据更新；手机 3D、实际材质变化和最新跨轮约束已回归。首次失败与重试见验收账本；时间是排练目标，不等于真人计时已通过。

## 0:00—0:40｜问题不是“不会选风格”

画面：用户回到家，面对客厅说出一句生活感受。

> 下班回到家，我坐在客厅，却还是像坐在工位。这句话没有风格名、家具名，也没有尺寸，但它是真实的设计起点。
>
> 我们是元界视创。OPAI 做的不是再生成一张效果图，而是帮助用户逐步说清楚生活需求，再把需求变成真实空间里看得见、改得动、能撤销的调整。

## 0:40—1:20｜企业为什么需要这一步

画面：生活表达 → 空间取舍 → 确认版本 → 专业交接。

> 全屋定制的前端沟通有一个长期难点：用户说的是生活，设计师需要的是明确的空间决定。哪些必须保留、哪里不能挡门，这些信息容易散落在聊天和不同版本图片里。
>
> 地方消费者调查和住宅案例说明，这类沟通、变更与落地摩擦真实存在；但我们不会说产品已经减少了多少返工。业务价值要靠门店或设计团队的对照试点验证。

## 1:20—2:00｜产品如何工作

画面：需求状态与统一场景的简图。

> OPAI 区分用户原话、AI 假设、已确认需求、约束和未决项。每轮只解决一个影响下一步的问题；信息够了，就给出可撤销尝试。
>
> AI 不能直接魔改房屋。当前户型、对象、尺寸和能力来自同一份场景事实；候选动作经过确定性规则校验，合法后才进入预览。用户确认之前，不覆盖已经保存的方案。

## 2:00—4:20｜一条真实演示

画面：最终候选的主工作台。必须标注实时、录屏、fallback 或固定脚本。

> 现在用一条没有写进脚本的新表达开始：这个客厅让我回到家还像坐在工位。

操作与旁白：

1. 展示 AI 的单个追问或可撤销尝试。
   > 这条未命中固定脚本的表达，实际由 DeepSeek-v4-flash 处理，没有静默切到预设。它先追问客厅里哪一点最像工位；方向相关，但还可以更具体，这是我们保留的体验改进。
2. 展示纠正、候选解释与 3D 差异。
   > 我纠正说：没有心理原因，我只是不喜欢冷灰色。DeepSeek 接受了纠正，没有残留心理假设。模型第一次生成无变化动作，系统没有伪装成功；修正后，只有合法的沙发材质命令进入真实 3D 可撤销预览。
3. 展示撤销、保留、保存和重开。
   > 这次调整可以撤销，也可以保留。独立验收已经完成保存和刷新重开，画面与版本保持一致。

演讲备注：旧 browser trace 的约束种类错误保留为失败；最新独立复测以两次模型调用完成纠正，仅沙发改为亚麻材质，其他家具材质和全部位置锁定。可展示这一真实结果，但不能说首次就成功、任意表达都可靠。实际脚本输入和页面结果不同时，按页面结果讲。

## 4:20—5:20｜家庭协作在后，不替用户做决定

画面：从已保存方案发起讨论 → 飞书意见 → Aily 摘要 → 用户选择 → 原项目新版本。

> 一个人使用到这里已经完整成立。只有方案保存后，用户才需要决定是否发起家庭讨论。
>
> 飞书收集原始意见，Base 记录项目和版本，Aily 只归纳意见记录的共同主题、表达差异和未决项；AI 不替家庭签字。这条后段已在隔离候选中真实跑通：Aily 逐项引用具体意见，用户选择后回到同一 DeepSeek 设计链，并保存新版本。
>
> 这次验证由同一隔离验收本人经 API 写入两条真实 Base 记录，没有第二个真实成员账号加入。我们证明的是飞书 AI 对意见内容的整理与版本回流链路，不冒充多个家庭成员已经真实共同使用。

## 5:20—6:10｜AI 深度与可信边界

画面：实际 provider、工具步骤、规则结果、版本链。

> 开放需求处理使用 DeepSeek-v4-flash；Astra 和 Sol 只用于开发。每轮记录实际模型、工具观察、来源、校验和版本变化。
>
> 模型负责理解和提出候选动作；场景事实、规则和版本守住写入。失败会明确显示，不会静默切成预设。
>
> 普通资料是带来源的参考，不会自动取得执行权限；我们保留过模型违反文字禁令的失败。用户确认的结构化规则才进入确定性校验。随后一次真实 DeepSeek 回合引用当前来源，选用允许的浅橡木墙板并排除灰米色。

## 6:10—6:45｜业务价值如何验证

画面：一个门店/设计团队的小范围验证表。

> 对用户，价值是把模糊感受变成自己能纠正、能撤销的空间决定。对设计师，价值假设是更早拿到确认需求、硬约束、版本差异和未决问题。
>
> 我们准备从一个真实品类和一组相近任务开始，记录需求遗漏、重大修改轮次、确认用时和因需求或版本不清产生的交接退回。现在没有真实试点结果，所以不编节省工时、成本或转化率。

## 6:45—7:00｜结尾

画面：用户确认后的空间与需求简报。

> OPAI 让 AI 不只会回答“怎么装修”，而是陪用户把生活说清楚，把每次选择落实到同一个家里，再把确认结果可靠地交给家人和专业设计师。谢谢。

## 高频答辩问题

1. **是不是固定脚本？**
   - 回答同次演示的真实来源：输入是否命中脚本、实际 provider/model、是否 fallback、哪些对象改变。固定脚本只证明交互流程，不能证明开放理解。
2. **为什么不是普通 3D 编辑器？**
   - 核心差异不是工具按钮，而是需求状态、跨轮硬约束、来源解释、受约束候选、撤销确认和版本交接连成同一条链。
3. **AI 做错怎么办？**
   - 模型只提候选动作；SceneCommand 与规则校验写入。多动作在副本中原子验证，失败不污染当前方案；用户还可撤销和纠正需求。
4. **飞书 AI 到底做什么？**
   - DeepSeek 做开放需求处理；飞书 Aily 整理真实 Base 中的意见记录；Base 保存版本关联与同步状态。Aily 不直接改场景，也不替用户决定。当前两条记录由同一隔离验收本人填写，没有第二个真实成员账号验证。
5. **节省了多少？**
   - 当前没有真实试点对照收益。说明准备如何测，不给虚构比例。
6. **有没有接入欧派真实数据？**
   - 还没有真实 SKU、报价、BOM、工期、施工和生产接口。当前只证明产品机制与可替换接入边界。
7. **能不能自动识别任意户型？**
   - 当前只对已确认并结构化的 canonical scene 负责；图片/PDF 可作为资料输入，但不能夸成任意户型自动建模。
