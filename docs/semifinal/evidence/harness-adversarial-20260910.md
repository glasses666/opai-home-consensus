# 设计 Agent Harness 刁钻输入实验（2026-09-10）

## 结论

原实现确实压制了 DeepSeek 的部分能力，但 Harness 本身不能拆掉。初始完整链路仅通过 4/8 个异于展示脚本的用例；极简控制提示对 5/5 个意图都给出了合理下一步，不过严格按 canonical scene 检查时只有 4/5 可执行，因为它虚构了不存在的 `opening-primary`。这说明主模型有足够的语义判断能力，而事实边界、原子执行和状态一致性仍必须由确定性 Harness 承担。

调整后的当前工作区在真实 DeepSeek 上通过主矩阵 8/8、留出矩阵 5/5。这个结果证明所列行为，不证明任意户型、任意家具和任意自然语言都已泛化。

## 实验设计与结果

### 初始完整 Harness 基线

主矩阵 8 个用例，4/8 通过、18 次模型调用。失败集中在：

1. 条件式只读检查无法正常结束；
2. 同一句互相冲突的位置要求没有稳定地暴露冲突；
3. 用户拒绝提供毫米数时，相对移动会卡在重复观察或错误修复；
4. 文字明确指向儿童房床，但页面旧选中仍干扰目标，并在失败候选后污染需求状态。

### 极简提示控制组

运行：

```bash
node scripts/probe_dialogue_raw_control.mjs --existing-opai-provider
```

5/5 个用例的语义下一步合理：识别只读、指出矛盾、自主选择保守位移、文字目标覆盖旧选中、接受用户否定心理推断。严格执行评分为 4/5：只读用例把不存在的 `opening-primary` 当成了场景对象。这一反例说明 DeepSeek 的推理空间需要释放，但 canonical ID 和执行安全不能交给纯提示词。

### 当前主矩阵

运行：

```bash
node scripts/eval_dialogue_adversarial.mjs --existing-opai-provider
```

最终当前工作区：8/8 通过，14 次模型调用。

| 用例 | 结果 | 关键行为 |
|---|---:|---|
| 条件式只读检查，不预览 | 通过 | 不写场景，不把未验证条件保存成永久锁 |
| 厨房岛台与冰箱均未建模 | 通过 | 明确 canonical scene 边界，不编位置、价格或动作 |
| 移茶几，同时所有家具不动 | 通过 | 明确冲突，只问保留哪一项，不写状态 |
| 沙发显沉，拒绝选颜色 | 通过 | 自主选择一个现有软包材质，只改材质且可撤销 |
| 茶几“稍微远一点”，拒绝毫米数 | 通过 | 先读取相对关系，再自主选择保守距离并通过规则 |
| 主卧文字目标覆盖旧选中 | 通过 | 只修改主卧地面，其他地面与家具位置锁定 |
| 儿童房床覆盖旧选中 | 通过 | 首个越界候选回滚，缩小距离后合法预览，其他家具不动 |
| 否定心理原因并改沙发颜色 | 通过 | reject 旧假设，只保留用户明确的颜色目标 |

### 留出矩阵

留出用例在主矩阵与提示词调整完成后才加入。第一次为 3/5：Harness 把逗号另一侧的“别动家具位置”误读成材质锁，也没识别“改单件材质 / 所有家具材质不变”的冲突。修正后当前工作区为 5/5，6 次模型调用：

```bash
node scripts/eval_dialogue_adversarial_holdout.mjs --existing-opai-provider
```

- 只读比较主卧床与衣柜材质；
- 钢琴不存在时不编造；
- 次卧床覆盖页面旧选中的沙发，且“忽略当前选中”不持久化；
- 用户否定心理推断后自主只改一种材质，所有家具位置保持；
- 单件家具改材质与“所有家具材质不变”同时出现时暴露冲突。

## 页面验收中发现并修复的额外失败

隐藏的 in-app browser 从首页创建独立项目，未操作用户前台。首次提交：

> 只判断一下：如果把客厅沙发再往电视墙方向推一些，会不会挡住主要通道？先不要修改；如果目前信息不足就直说还需要多少距离，不要猜。

DeepSeek 虽然诚实说信息不足，却仍心算并声称“最多约 430mm”，且方向推理不自洽；同时把“先不要修改”保存成永久 `lock_transform`。这两个失败没有从分母删除，随后增加了以下门禁：

- 没有假设位移验证结果时，不允许根据中心点、尺寸或旋转角引入余量、净宽、极限位移等派生数值；
- “本轮/先/暂时不改”及未验证的“如果…就…”条件不持久化成永久硬约束；
- `clarify` 的解释与问题分处两个 JSON 字段时，界面合并展示，不再丢掉追问。

最终隐藏页面复测：项目 `exp-90dc993c-be15-4bd4-978a-9e8e80c47e1b`，请求 `fc90485d-64bf-4f7d-b6a7-11dee749c052`，3.9 秒，真实来源 `deepseek · deepseek-flash`，结果 `clarify`。页面只显示一个待明确项，场景未写入、没有永久硬约束，并明确询问计划移动多远。

## Harness 调整

- 增加终态 `answer`，只读请求可以在观察后正常结束；终态禁止夹带工具调用。
- 将“本轮不改”“忽略当前选中”等路由语句与长期需求分离。
- 显式识别位置冲突、材质冲突、文字点名房间和 canonical scene 中缺失对象。
- 失败候选恢复尝试前需求快照；同一读工具不重复，无新观察时退出；新观察后才允许修正写动作。
- 相对移动必须先获得精确对象对关系；越界候选完整回滚后可按错误缩小距离。
- 对“其他家具不动”等范围用 canonical scene 确定性展开，不把范围枚举负担留给模型。
- 拒绝同一属性被连续覆盖、回复声称未实际预览的材质、未经验证的反事实数值。
- 追问和解释都保留在可见回复中，用户纠正的 quote、假设 reject 与约束状态继续可追溯。

## 仍然存在的边界

- 当前 counterfactual 没有只读的“在副本中模拟但不产生预览”工具；缺少移动距离时会追问，不会替用户验证一个不存在的假设。
- 规则路由仍包含有限的中文显式措辞检测；13 个用例和一次 GUI 流程不是开放域证明，新增同类失败应继续进入留出回归。
- 当前场景的对象、能力和资料边界决定可执行范围；缺失家具不会被凭空创建。
- 本轮验证的是本地完整资源与真实 provider，不等于公网时延、生产配置或任意新户型已通过。
